最终固件：clean build `4316c267`（p7）

## 〇、背景与目标

M2.2 验收项是"FreeRTOS 跑在 core1（物理 core3）"，之前 core1 的调试输出
打在 UART2（与 Linux 共用调试口）。正式方案：**core1 控制台迁移到 UART4
（40pin，uart4m1：GPIO3_B1=RX / GPIO3_B2=TX，基地址 0xFE680000）**，
UART2 完全还给 Linux。

core1 在 u-boot 阶段启动、Linux 尚未初始化 UART4，且 dts 已把 uart4 设为
disabled（Linux 不再占用）——所以 core1 必须自行完成三步初始化：

```
① CRU 时钟：SCLK_UART4 mux 选 xin24m（24MHz）+ 去 gate
② IOC 引脚：GPIO3_B1/B2 配成 UART4 功能（mux=4，uart4m1）
③ UART4 寄存器：波特率 1500000 / 8N1（div = 24M/(16×1.5M) = 1）
```

寄存器（TRM + clk-rk3568.c / pinctrl-rockchip.c 核对）：

| 寄存器 | 地址 | 作用 |
|---|---|---|
| CRU_BASE | 0xFDD20000 | 普通域时钟 |
| CLKSEL_CON(58) | 0x100+58×4 = 0x1E8 | sclk_uart4 mux [13:12]、src_sel [9:8]、div [6:0] |
| CLKGATE_CON(28) | 0x300+28×4 = 0x370 | 位8=PCLK_UART4、位11=SCLK_UART4（1=关 0=开） |
| IOC/GRF_BASE | 0xFDC60000 | 引脚复用 |
| GPIO3B_IOMUX | 0x48 | B1 位[7:4]、B2 位[11:8]，mux=4 |

## 一、教学铺垫：读手册的关键认知（本次调试的基础）

### 1.1 CRU 寄存器怎么选（"CLKSEL_CON 有几十个，用哪个？"）

- **索引表 ≠ 选择依据**：2.4 开头的寄存器索引表 Description 全是
  "Internal clock select and division register N"，不告诉你对应哪个时钟。
- **真正的映射在逐寄存器位域描述里**：字段名就是信号名（如 `sclk_uart4_sel`）。
- **正确方法 = 按信号名搜索**：Ctrl+F "uart4" → 得到 CON58（mux/div）、
  CON59（frac）、GATE_CON28（gate）。编号 nn 只是设计顺序，不是外设号。
- **注意域**：uart0 的时钟在 PMUCRU（0xFDD00000），不是主 CRU！
- **禁区**：CLKSEL_CON00/01 是 clk_core0-3_div（CPU 核心时钟），乱碰死机。

### 1.2 位域语法与 HIWORD_MASK

- `2'b10` = Verilog 位宽语法：2 位二进制数 10 = 十进制 2，对应 [13:12]=2。
- 所有 CRU/GRF 寄存器是 HIWORD_MASK 设计：**高 16 位是低 16 位的逐位写使能**
  （第 n+16 位放行第 n 位数据）。
- **使能位的"F 个数" = 字段位宽**：4-bit 字段 → 0xF；2-bit → 0x3；1-bit → 0x1。
  少使能一位，那一位保留旧值 → 字段可能变成未定义功能。
- GRF 章节的 3-bit 描述是旧模板，RK3568 实际是 4-bit IOMUX_SEL 布局
  （UART 章节 Table 25-1 + pinctrl 驱动 IOMUX_WIDTH_4BIT + 实测三重印证）。

## 二、阶段一：UART4 完全无输出 —— mkimage 打包坑

### 症状
烧新固件后 UART4 完全无输出；**UART2 上连 [DIAG]/[core1] 都没有**。
当时的关键判断：core1 压根没被启动（不是 UART4 没配好，是固件没跑起来）。

### 排查步骤（命令 + 思考）
1. 抓完整启动日志（u-boot 起）：
   ```bash
   python3 /tmp/bootcap.py   # 发 reboot + 串口抓 40s → /tmp/bootlog.txt
   grep -n "AMP" /tmp/bootlog.txt
   ```
   结果：`AMP Error: No totalsize` —— u-boot 的 amp_cpus_on() 解析 p7 的 FIT 失败。

2. 查 p1 里跑的 u-boot 是否有 M2.1 的修复（4KB→4MB 读窗口）：
   ```bash
   dd if=/dev/mmcblk0p1 bs=512 2>/dev/null | grep -a -c 'read amp partition failed'
   ```
   结果：2 → 修复在。但 fit_get_totalsize 仍失败。

3. 本地解析 FIT 字符串表（python 解析 FDT）：
   ```python
   data = open('amp.img','rb').read()
   off = struct.unpack('>I', data[12:16])[0]   # off_dt_strings
   strs = data[off:].split(b'\x00')
   print(b'totalsize' in strs)
   ```
   结果：**字符串表里没有 "totalsize" 属性名！**

4. 对比两套 mkimage 的输出：
   ```bash
   # Ubuntu 系统 mkimage（PATH 里默认）：
   /usr/bin/mkimage -V          # 2022.01+dfsg-2ubuntu2.7
   # SDK u-boot 自带 mkimage：
   .../u-boot/tools/mkimage -V   # 2017.09
   ```
   结果：**SDK mkimage 生成 FIT 含 totalsize+version；Ubuntu 的不含。**

### 根因
u-boot 的 `fit_get_totalsize()`（common/image-fit.c）用
`fdt_getprop(fit, 0, FIT_TOTALSIZE_PROP, NULL)` 按**属性名**查 "totalsize"
（image.h:925 `#define FIT_TOTALSIZE_PROP "totalsize"`）。
之前验证成功的 456026e8 一直用 SDK mkimage；某次构建环境 PATH 变成了
Ubuntu 系统 mkimage → 打包出的 FIT 缺 totalsize → u-boot 解析失败 →
**core1 从未被加载** → UART2/UART4 全静默，Linux 正常（它在 boot.img）。

### 修复
Makefile 固定用 SDK mkimage，并加注释说明坑：
```make
SDK_MKIMAGE := .../u-boot/tools/mkimage
amp.img: core1.bin amp.its
	$(SDK_MKIMAGE) -f amp.its amp.img
```
验证：`AMP: Brought up cpu[300] with state 0x12, entry 0x07000000 ...OK` ✓
DIAG 全对：`clksel58=0x2000`（mux=2 + div=0）、`gate28=0x0`、`iomux=0x440`、
`lcr=0x3`、`lsr=0x60`。

## 三、阶段二：干净版卡死 —— 时序竞争

### 症状
mkimage 修好后（5804e925，干净版+CRU 修正），UART4 只出：
```
=== core1 FreeRTOS (M2.2) ===
el = EL1
```
之后**再无任何输出**。UART2 无 [FATAL]/[EXC]（configASSERT 打 UART2，能确认）。

### 用户建议与我的判断
用户建议"把寄存器修改改回原来的"。判断：**banner 能正常显示 = UART4 时钟/
波特率全对 = CRU 修正无辜**（寄存器最终状态和验证成功时一致，读回已确认）。
卡点在 `el = EL1` 之后的 gic_init/建队列/建任务/起调度器，与 CRU 无关。
→ 改用"加标记定位"而不是盲回退。

### 二分定位全过程（自诊断设计）

| 实验 | md5 | 内容 | 结果 | 证据 |
|---|---|---|---|---|
| v1 | 19b7f255 | M1-M5 + T1 first-run | 到 T1 first-run | UART2 标记 |
| v2 | 98f6b4fd | 全标记（M/T1/IRQ） | ✅ 全通 | IRQ 每秒~800 次，T1A-D 全过，U4LSR=0x60 |
| clean | 57a1608c | 零标记 | ❌ 卡 | 用户 UART4 确认 |
| testA | 9f14e661 | 干净+只加 IRQ fired/done | ✅ 通 | 32086 次 "IRQ done" |
| testB | fd9c4d84 | 干净+移除 port.c ICC_RPR 断言 | ❌ 卡 | RPR 断言无辜 |
| testA1 | 62f0c709 | 干净+只加 IRQ fired | ❌ 卡 | **0 次标记 = 首个 tick 前就挂** |
| testD | 102dd718 | 干净+只加主函数 M1-M5 | ✅ 通 | M1-M5 全过 |
| testG | cf1b5e0d | 干净+调度器前纯延时 3ms | ✅ 通 | **纯时序实锤** |
| testH | 4316c267 | 干净+gic_init 末尾 settle 3ms | ✅ 通 | **正式修复** |

### 关键思考
1. **独立编译单元推论**：gic.c/queue.c/tasks.c/port.c 是分开编译的，
   机器码在所有版本里**完全相同**——它们不可能"时好时坏"。
   唯一变量是 main()/vTask1/vApplicationIRQHandler 里标记带来的**打印时序**。
2. **testA1 的 0 次标记**（连 IRQ fired 都没有）→ 卡点在**首个 tick 之前**，
   即调度器启动窗口 → 把目光从中断路径移到调度器前的时序。
3. **testD 证明 M 标记（主函数里 gic_init 后的 ~2.5ms 延迟）就是解药**。
4. **testG 用纯延时循环（不碰串口）复现成功** → 是"延迟"在起作用，
   不是打印的副作用。

### 正式修复（testH）
```c
/* gic.c gic_init() 末尾 */
__asm volatile("isb");
for (volatile uint32_t d = 0; d < 3000000u; d++) ;   /* ~3ms GIC settle */
```
- main.c 零调试痕迹；延时语义上属于 GIC 初始化的一部分
- 机理（实证）：gic_init 完成后立即启动调度器 arm tick/开 IRQ，
  GIC 尚未完全就绪，首个 tick 竞态导致 core1 静默卡死。确切硬件环节
  未深挖（GICD/GICR/CPU 接口哪个需要 settle），但 ~ms 级等待实证有效。

## 六、经验教训汇总

1. **先判断"固件到底跑没跑"**：UART2 连 [DIAG] 都没有 → 查加载层（u-boot/
   FIT），别一头扎进外设配置。
2. **工具链一致性**：mkimage 这类打包工具版本不同输出不同（totalsize 属性），
   必须固定并在 Makefile 里注释原因。
3. **二分时序问题**：先加满标记确认能跑，再逐个删组，定位"哪组标记是解药"；
   用"标记是否刷屏"做自诊断，减少来回换线。
4. **独立编译单元推论**：跨单元函数机器码不变 → 现象差异必然来自调用方时序。
5. **读回验证**：CLKSEL/GATE/IOMUX/LSR 全部读回，配置对错一目了然。
6. **串口救急通道**：无网络时 base64 分块传文件；注意 echo 换行与丢块。
7. **TRM 复位值 ≠ 硅片真相**：读回验证才知道芯片实际状态。
