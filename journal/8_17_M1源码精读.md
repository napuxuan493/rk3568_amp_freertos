## 五个源码问题的最终答案（验收通过版）

**Q1：TCB 哪些字段是调度必需的？**
- `pxTopOfStack`：**当前栈顶指针**（调度最核心——上下文切换时任务现场存这里）
- `uxPriority`：优先级（0 最低）
- `xStateListItem`：状态链表节点（Ready/Blocked/Suspended 由它挂在哪条链表决定）
- `xEventListItem`：事件链表节点（等待队列/信号量时的挂接点）
- `pxStack`：栈起始（栈检查/释放用）
- `uxBasePriority`：基础优先级（优先级继承还原时用）

**Q2：vTaskDelay 内部做了什么？**
- 剥壳后真身 3 行：延迟>0 → `prvAddCurrentTaskToDelayedList`（把自己从就绪链表摘下、放进延迟链表、记唤醒时间）→ `portYIELD_WITHIN_API` 主动让出 CPU
- 时间到：tick 中断里 `xTaskIncrementTick` 把它从延迟链表搬回就绪链表
- 实验 P1 的"delay 500ms 后继续"就是这三行循环工作

**Q3：信号量为什么是队列的一种？**
- 二进制信号量 = **容量 1、初始 1** 的队列；计数信号量 = 容量 N
- Take = 取走那 1 个元素（取走时阻塞），Give = 放回 1 个元素
- 与队列同源（`xQueueSemaphoreTake` 调底层同一套取/放机制），只是**不拷贝数据、计数代替内容**

**Q4：就绪链表结构 + 怎么选任务？**
- ★ 关键修正：**不是一条从高到低的长链表**，而是 **`configMAX_PRIORITIES` 条链表组成的数组**（每个优先级一条，`pxReadyTasksLists[prio]`）
- 任务永远挂在自己优先级那条链表上
- 选任务：`uxTopReadyPriority` 位图找最高非空链表 → 从链表头部取（`taskSELECT_HIGHEST_PRIORITY_TASK`）
- 印证：`vTaskPrioritySet` 里 `pxReadyTasksLists[uxPriorityUsedOnEntry]` 的下标就是优先级

**Q5：优先级继承在哪实现？**
- 触发点：`queue.c` L1701（`xQueueSemaphoreTake`）——高任务等锁时发现持有者优先级比自己低 → `xTaskPriorityInherit`
- 实现：`tasks.c` L4135——比一比（持有者 < 我）→ 提一提（持有者临时升到我优先级）→ 挪链表（重新挂就绪链表）
- 还原点 1：持有者释放锁时恢复原优先级
- 还原点 2：等待者**超时放弃**时 `vTaskPriorityDisinheritAfterTimeout`（tasks.c L4305）——注意还原到 `max(原优先级, 剩余等待者最高优先级)`，不是一律还原到原值
- 实验 P4 现象解释：低任务(1)被高任务(3)继承提升 → 中任务(2)抢不过 → 低任务跑完释放 → 高任务拿到锁
- `xQueueGiveMutexRecursive` 是递归锁释放（计数减到 0 才真还），不是继承本身

## 三个收获

1. **FreeRTOS 源码是"宏 + C"的模板化编程**：`trace*`/`mtCOVERAGE*`/`configASSERT`/`PRIVILEGED_*` 在默认配置下全是空壳，约 80% 的可见代码是其他配置的死代码——拿到"阅读地图"后其实不深。
2. **链表项自带容器指针（`pxContainer`）**：`listIS_CONTAINED_WITHIN` O(1) 判断"我在哪"，和 Linux `container_of` 同一哲学；就绪链表是"按优先级索引的数组"，不是一条长链表。
3. **互斥锁的优先级继承 = 借优先级**：高任务把优先级"借"给持锁者防中任务插队，等锁/释放时归还——P4 实验全程就是这个机制在跑。
