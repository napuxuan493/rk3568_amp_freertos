## 1. 阶段一（8_18~8_20）：两条失败路线的探索——为什么都走不通

### 1.1 路线 A：Linux 侧 CPU 热插拔启动 core3 —— 被 OP-TEE 堵死

尝试：`echo on 3` / `echo on 0x300 > /sys/devices/system/cpu/cpu3/online`
现象：`cpu[3] is unavailable`（sysfs id 要用 MPIDR 值 0x300）；`CPU_ON ret=-5`（EIO/EINVAL）。

根因（源码级）：OP-TEE（BL32，`rk3568_bl32_v2.15.bin`）负责次级核上电，它每次 CPU_ON
都打印 `I/TC: Secondary CPU 3 ... switching to normal world boot`，但对**已被启动过的核
再次上电会失败**。也就是说：core3 一旦被 boot 过一次，就再也不能 re-online。
→ 结论：core3 只能**首次**由 u-boot 在引导期拉起来，Linux 侧永远不碰它。

配套保护（dts，`kernel/arch/arm64/boot/dts/rockchip/rk3568-amp.dtsi`）：

```dts
&cpu3 { status = "disabled"; };          /* Linux 根本不知道 core3 存在 */

rockchip-amp 节点：                       /* 保留 core1 要用的外设时钟，防止被 gate */
    clocks = <&cru SCLK_UART4>, <&cru PCLK_UART4>, <&cru PCLK_TIMER>,
             <&cru CLK_TIMER4>, <&cru CLK_TIMER5>, <&cru ACLK_MCU>;
    /* amp-cpus 节点已移除：否则 u-boot 会把 core3 标记为 os-dispatcher 所有而跳过启动 */

reserved-memory {
    core1-fw@7000000  { reg = <0x0 0x7000000 0x0 0x100000>; no-map; };  /* 固件+栈 1MB */
    amp-shmem@7800000 { ... }; rpmsg@7c00000 { ... };
    rpmsg-dma@8000000 { compatible = "shared-dma-pool"; ... }; mcu@8200000 { ... };
};
```

**为什么必须 no-map 保留 0x7000000**：裸机固件直接写物理地址。若 Linux 把它当普通 RAM，
可能分配走并踩掉固件；且本内核 `__ioremap` 拒绝 RAM 地址（`WARN_ON(pfn_valid)`），
`/dev/mem` 又被 `devmem_is_allowed` 挡住——固件区必须是不映射的保留内存。

### 1.2 路线 B：u-boot 控制台操作 —— 被安卓启动流程重拼 cmdline 堵死

尝试过的操作（全部无效/被拒）：`setenv bootargs ...`、`gpt write mmc 0 ...`、手动 `bootm 0x1000000`、`boot_android mmc 0`。

根因（源码级）——cmdline 不是由 env 决定的，`common/android_ab.c` 的 `ab_update_root_uuid()`：

```c
/* android_ab.c:422 */
char root_partuuid[70] = "root=PARTUUID=";
...
if (!strstr(boot_args, "root=")) {          /* bootargs 里没有 root= 才补 */
    get_partition_unique_uuid(ANDROID_PARTITION_SYSTEM, guid_buf, UUID_SIZE);
    strcat(root_partuuid, guid_buf);         /* 按 GPT 里 system 分区实际 GUID 拼 */
    env_update("bootargs", root_partuuid);
}
```

Android 流程（`boot_android`）会**重建** cmdline（镜像自带 cmdline + env bootargs 拼接，
最后一个 `root=` 生效）；日志明确打印 `Not AVB images, AVB skip`——**不是签名验证挡住，
是流程逻辑重拼**。所以手动 setenv 要么被拼回去、要么被自动补全接管。

`gpt write` 的问题：u-boot 的 gpt 命令把第一个分区放在 LBA 34，而 Rockchip 布局要求
第一个分区在 LBA 0x4000（8MB loader 间隙），一写整体错位，boot 直接找不到。

**阶段结论**：任何运行时（控制台/env）手段都不可靠 → 唯一的出路是**改 SDK 源码 + 重烧镜像**。
另外在此阶段确认了 `/dev/mem` 被禁、内核 ioremap 拒 RAM 等约束，决定了固件必须住进 no-map 保留区。

## 2. 阶段二（8_21）：M2.1 达成——官方 u-boot amp + FIT 流程

### 2.1 源码级修复①：parameter.txt 的 uuid 行（修复 system GUID 随机）

**症状**：重烧后内核卡 `Waiting for root device PARTUUID=614e0000-0000`。
**根因**：`di -p` 重建 GPT 时，没有 `uuid:` 行的分区被 upgrade_tool **随机生成 GUID**
（工具二进制里有 `gen_rand_uuid`）；而 cmdline 的 `root=PARTUUID=614e0000-0000` 是前缀匹配。
**修复**（对照 SDK 官方 `parameter-buildroot-fit.txt`——它本来就有 uuid 行，我们弄丢了）：

```ini
# rockdev/parameter.txt（mtdparts 与官方 FIT 布局一致：boot/boot_b 双槽 + amp 分区）
CMDLINE: mtdparts=:0x00002000@0x00004000(uboot),0x00002000@0x00006000(misc),
0x00020000@0x00008000(boot),0x00020000@0x00028000(boot_b),
0x00c00000@0x00058000(system),0x00040000@0x00c58000(oem),
0x00010000@0x00c98000(amp),-@0x00ca8000(userdata:grow)
uuid:system=614e0000-0000-4000-8000-000000000000   ← 系统分区固定 GUID
uuid:boot=7A3F0000-0000-446A-8000-702F00006273
```

验证：`blkid` 显示 `p5 system PARTUUID=614e0000-...`，`root=PARTUUID=614e0000-0000` 前缀匹配成功。
⚠️ 注意：upgrade_tool 的**本地** `GPT` 命令会忽略 uuid 行，但 `di -p`（设备流程）会采纳。

### 2.2 源码级修复②：amp_cpus_on 的 4KB 读窗口 bug（最漂亮的一个）

**症状**：amp.img ≤ ~3.6KB（test_A，payload 2048B）u-boot 能解析并拉起 core3；
换完整固件（6671B）报 `AMP Error: No totalsize`。
**根因**（`u-boot/drivers/cpu/rockchip_amp.c` 原始代码）：

```c
hdr = memalign(ARCH_DMA_MINALIGN, FIT_HEADER_SIZE);   /* 只读 4KB */
cnt = DIV_ROUND_UP(FIT_HEADER_SIZE, part.blksz);      /* 8 扇区 */
blk_dread(dev_desc, offset, cnt, hdr);
if (fit_get_totalsize(hdr, &totalsize)) {             /* ← 挂在这 */
    AMP_E("No totalsize\n");
```

而 `fit_get_totalsize` 是这样找 "totalsize" 的（`common/image-fit.c`）：

```c
int fit_get_totalsize(const void *fit, int *totalsize) {
    val = fdt_getprop(fit, 0, FIT_TOTALSIZE_PROP, NULL);  /* 按属性"名字"查 */
```

**FDT 的属性名存在文件末尾的字符串块（off_dt_strings）**。用 python 解析 FDT 头
（off_dt_strings 在头偏移 12）得到：

```
旧 FIT（3675B）: off_str = 0x0A15 → 2581 < 4096 ✅ 在 4KB 窗口内
新 FIT（6671B）: off_str = 0x15CC → 5580 > 4096 ❌ 越界
```

即：FIT 一超过 ~4KB，字符串块被推到读窗口外，`fdt_getprop` 拿到越界指针，
名字查不到 → "No totalsize"。**官方 RTOS 构建用 `mkimage -E`（外置数据），FIT 结构永远 ~1KB，
从没踩中**；我们内联数据把结构撑大才触发。

**修复**（把"只读 4KB 头"改成"读分区前 4MB 有界前缀"，并加错误打印）：

```c
#define AMP_READ_BLOCKS  (SZ_4M / 512)
hdr = memalign(ARCH_DMA_MINALIGN, SZ_4M);
cnt = (int)(part.size < AMP_READ_BLOCKS ? part.size : AMP_READ_BLOCKS);
if (blk_dread(dev_desc, part.start, cnt, hdr) != cnt) {
    AMP_E("read amp partition failed (%d blocks)\n", cnt);   /* 失败可见 */
    ...
}
```

**过程中踩的两个坑**：① 第一次补丁读整分区 32MB → 超过 dwmmc 的 16 位块数上限
（0x10000 blocks），`blk_dread` 静默失败（没加错误打印，查了半天 .config 确认
CONFIG_AMP 还在才推断出来）；② 编译器 `-Werror` 把未用变量当错误。教训：**失败路径
必须留打印**。

### 2.3 core1 固件源码解析（M2.1）

#### startup.S —— 裸机入口，第一件事是关 MMU/缓存

```asm
/* 1. 先关 MMU/D-Cache/I-Cache —— ATF/OP-TEE 留给 core3 的 MMU 是开的！ */
mrs     x0, sctlr_el1
bic     x0, x0, #(1 << 0)      /* M:   MMU */
bic     x0, x0, #(1 << 2)      /* C:   D-Cache */
bic     x0, x0, #(1 << 12)     /* I:   I-Cache */
msr     sctlr_el1, x0
isb                             /* 之后物理地址直写直达硬件 */
/* 探针 "CORE" @0x7002000；栈 _stack_top；向量表 vbar_el1；清 BSS；bl main */
```

**为什么必须关**：test_A.S 不关 MMU，第一条 `str` 写 UART 物理地址就翻译失败/滞留在 L1
缓存 → 外部完全看不到。startup.S 的注释里写着这是上次调试的教训——
"core3 的写可能滞留在 L1，Linux 的 ioremap 读和 UART 硬件都看不到"。

#### test_A.S 的假阳性教训

test_A.S 往 UART2 THR 死循环写 'A'。首次测试日志里数出 179 个 'A' 以为 core1 在跑——
**后来用"连续 AA 串"甄别，发现全是大写文本噪声（"AArch64" 里的 A+A），core1 实际零输出**。
真正的验证要区分"程序输出"和"文本巧合"。

#### main.c / uart.c / link.ld

```c
/* main.c：打印身份后死循环（M2.1） */
uart_puts("mpidr   = "); uart_puthex(read_mpidr());   /* 0x81000300 → core3 */
uart_puts("el      = EL"); uart_putdec(read_currentel() >> 2);  /* EL1 */
```

```c
/* uart.c：8250 兼容轮询写。测试变体把基地址改到 UART2（调试口 1500000） */
#define UART4_BASE  0xFE660000UL   /* 测试：UART2 调试口（40pin 的 UART4 没人看） */
#define UART_THR    0x00
#define UART_LSR    0x14
void uart_putc(char c) { while (!(REG(UART_LSR) & (1u<<5))); REG(UART_THR)=c; }
/* uart_init() 空实现：复用内核/u-boot 已配好的 1500000/8N1 */
```

```ld
/* link.ld：VMA = LMA = 0x7000000（加载即运行，无 AT()），三处必须一致：
 * link.ld . / amp.its load / dts core1-fw 保留区 */
. = 0x7000000;
.text : { KEEP(*(.text.start)); . = ALIGN(2048); KEEP(*(.text.vectors)); *(.text*) }
.rodata : { *(.rodata*) }  .data : { *(.data*) }
.bss : { __bss_start = .; *(.bss*) *(COMMON); __bss_end = .; }
. += 0x8000;  _stack_top = .;   /* 32KB 栈 */
```

**链接脚本 ↔ 代码的"接头"机制**：`. = 0x7000000` 设 VMA；`_stack_top`/`__bss_start` 是
脚本定义符号，startup.S 用 `ldr x0, =_stack_top` 引用——汇编阶段留下重定位记录
（`R_AARCH64_ABS64 _stack_top`），链接阶段按脚本布局填成绝对地址（如 0x70093c0），
objcopy 成裸二进制后地址烤死在字面量池里。u-boot 必须把二进制**原样加载到 0x7000000**
（amp.its 的 `load=<0x07000000>`），否则所有绝对引用全错。

#### amp.its —— FIT 元数据（data-size 必须显式声明）

```dts
core1 {
    data = /incbin/("/home/na/rk3568_amp/core1/core1.bin");
    data-size = <0x10000>;   /* ★ 该 u-boot 的 fit_image_get_data_size 只认这个属性 */
    type = "firmware";  arch = "arm64";  compression = "none";
    load = <0x07000000>;  entry = <0x07000000>;
    cpu = <0x300>;  boot-on = <1>;  hyp = <0>;  thumb = <0>;

```

**PE_STATE 解码**（`u-boot/include/amp.h`）：bit1=AArch64、bit2=EL2、bit3=thumb、bit4=非安全。
`hyp=<0>` → 非 EL2，加上 AArch64+非安全 = state 0x12 → core3 从 **EL1 非安全**进入
（与 hello 打印的 `el = EL1` 一致）。

## 3. 阶段三（8_22）：M2.2 达成——FreeRTOS + GICv3

### 3.1 大图：FreeRTOS port 是 GICv2 写的，RK3568 是 GICv3

`freertos-kernel/portable/GCC/ARM_CA53_64_BIT`（V10.6.2）的 CPU 接口全走 **MMIO GICC**
（`portICCIAR_OFFSET 0x0C` 等），而 GICv3 的 CPU 接口是 **ICC_*_EL1 系统寄存器**。
RK3568 的 GIC 节点只有 GICD/GICR（`arm,gic-v3`），没有 GICC 别名 → 必须适配。

### 3.2 适配点（源码级，全部实测）

**portASM.S**（3 处）：

```asm
/* ① IRQ ack：GICv2 内存映射 → GICv3 系统寄存器（binutils 2.36 只认 s3_0_ 编码） */
MRS     X0, s3_0_c12_c12_0            /* ICC_IAR1_EL1 */
/* ② IRQ eoi */
MSR     s3_0_c12_c12_1, X0            /* ICC_EOIR1_EL1 */
/* ③ portSAVE_CONTEXT 的 PMR 写 */
MSR     s3_0_c4_c6_0, X1              /* ICC_PMR_EL1 */台/bootargs（安卓安全流程不允许），只做源码级修改 + 重烧。

/* ④ FreeRTOS_Abort → b abort_handler（非 SVC 同步异常也可见，不静默死循环） */
```

**port.c**（4 处）：

```c
/* PMR 读写（portCLEAR_INTERRUPT_MASK / uxPortSetInterruptMask / FreeRTOS_Tick_Handler） */
__asm volatile ( "MSR s3_0_c4_c6_0, %0" :: "r"(val) );   /* ICC_PMR_EL1 */
__asm volatile ( "MRS %0, s3_0_c4_c6_0" : "=r"(val) );
/* BPR 校验 → ICC_BPR1_EL1（s3_0_c12_c12_3）*/
/* 优先级检查偏移 0x400 → 0x420（GICD_IPRIORITYR8，见 3.3 坑③）*/
/* RPR 校验 → ICC_RPR_EL1（s3_0_c12_c11_3）*/
```

**编译必须 `-DGUEST`**：port 用 `#if defined(GUEST)` 选择 EL1 路径（SPSR_EL1/ELR_EL1、
`portYIELD()=SVC 0`）；不定义它会去读 SPSR_EL3 直接 trap。

**向量表路由**（startup.S）：同步异常槽 → `FreeRTOS_SWI_Handler`（portYIELD 的 SVC 走这），
IRQ 槽 → `FreeRTOS_IRQ_Handler`，FIQ/SError → `abort_handler`（打印 ESR/FAR/ELR/SP）。
符号 `_freertos_vector_table` 是 port 要求的名字（`vPortRestoreTaskContext` 会 MSR VBAR_EL1）。

**tick 链路**（自定义）：`configSETUP_TICK_INTERRUPT()` → `vPortSetupTimerInterrupt()`
（timer.c：写 `CNTP_TVAL_EL0`=24MHz/1000、`CNTP_CTL_EL0`=1 使能）；
`configCLEAR_TICK_INTERRUPT()` → 重新装填 TVAL（清 ISTATUS，level 中断必须清条件）。
tick ISR：向量表 IRQ 槽 → portASM.S 存上下文 + ack → `vApplicationIRQHandler(INTID)`
→ INTID==30 → `FreeRTOS_Tick_Handler()`（port.c：xTaskIncrementTick）。

**GICv3 最小初始化**（gic.c，顺序）：

1. GICD_CTLR 置 EnableGrp1NS（EL1 非安全视角只有 bit1 可写）
2. GICR_WAKER 清 ProcessorSleep，等 ChildrenAsleep
3. 配置 PPI 30：IGROUPR0→Group1、IPRIORITYR7 字节通道 2→0xE0、ICFGR0→level、ISENABLER0 使能
4. GICD_IPRIORITYR8 = 0xFF（喂 vPortValidateInterruptPriority，见坑②）
5. ICC_SRE_EL1=0x7 / ICC_PMR_EL1=0xFF / ICC_BPR1_EL1=0 / ICC_IGRPEN1_EL1=1

### 3.3 六个坑（每个都是真实的调试课）

**坑① binutils 2.36 不认 `icc_*_el1` 寄存器名** → 全部用 `s3_0_...` 编码
（PMR=s3_0_c4_c6_0、IAR=s3_0_c12_c12_0、EOIR=s3_0_c12_c12_1、BPR1=s3_0_c12_c12_3、
SRE=s3_0_c12_c12_5、IGRPEN1=s3_0_c12_c12_7、RPR=s3_0_c12_c11_3）。

**坑② GIC 只有 4 位优先级（16 级）**：往 GICD_IPRIORITYR8 写 0xFF 读回 0xF0。
→ `configUNIQUE_INTERRUPT_PRIORITIES` 必须是 **16**（不是 256）。
连带：`vPortValidateInterruptPriority` 的 `while ((v&1)!=1) v>>=1` 在读到 0 时**死循环**。

**坑③ GICv3 下 GICD_IPRIORITYR0 恒为 0**：SGI/PPI 优先级在**重分发器**里
（GICR_IPRIORITYRn @ RD+0x10400），分发器的 R0-R7（INTID 0-31）是 RES0。
→ port 的优先级检查偏移从 0x400 改成 0x420（第一个 SPI 的优先级，GICD_IPRIORITYR8）。
证据：写 R0 读回 0（`sgi-pri=0`），写 R8 读回 0xF0。

意思就是在 GICv3 里，GICD 已经“无权过问” INTID 0~31 的事情了。因此，GICD 里的 GICD_IPRIORITYR0 到 GICD_IPRIORITYR7（刚好覆盖 0~31 号中断）在硬件物理层面上被定义成了 RES0 (Read-As-Zero, Writes Ignored)。这就是为什么你往 GICD_IPRIORITYR0 写任何值，读出来的永远是 0。你要配 30 号定时器的优先级，必须去 GICR_IPRIORITYRn 里配。  

**坑④ tick PPI = INTID 30**（不是 26/27，更不是 20）：
+ 内核跑 **VHE(EL2)**（dmesg: `CPU: All CPU(s) started at EL2`），CNTP_EL1 被重定向到
  CNTHP_EL2 → /proc/interrupts 显示 arch_timer 在 **26**（这是 EL2 的假象！）
+ 我们在 EL1 用 CNTP_EL0（不重定向）→ 真 PPI = **30**（= dts `GIC_PPI 14`）
+ 定位方法：先全使能 PPI 16-31，统计每个 INTID 触发次数——启动时 ~14 个 PPI 各触发
  一次（u-boot 期间积压的 pending 排空），之后 30 持续重复（26 次 vs 其他各 1 次）
+ **教训**：单 PPI 20 测试失败是排空噪声误导；"全 PPI + 统计重复"才可靠
****************这里其实不需要测试，ppi30对应的才是CNTP定时器的中断资源***************

**坑⑤ "core1 死在内核启动前"是误诊**：tick 停止（PPI 配错）→ 任务全冻结在 vTaskDelay →
看起来像死了。tick 恢复后任务**全程存活**（48 条打印出现在内核启动之后）——没有
cpuidle 杀核问题。

**坑⑥ SVC 槽指错直接崩**：vTaskDelay → portYIELD → `SVC 0` → 若同步异常槽指到
abort_handler 会打印 `[EXC] esr=0x56000000`（SVC 指令异常）；必须指到
FreeRTOS_SWI_Handler（port 的上下文切换入口，内部按 ESR 区分 SVC/其他）。

### 3.4 调试方法论（本阶段用到的）

1. **崩溃可视化**：向量表非 IRQ 槽全指 abort_handler（打印 ESR/FAR/ELR/SP），
   静默挂死 → 变成可见 [EXC]
2. **逐步标记**：gic_init 里插 `gic1/2/3/4`、xPortStartScheduler 里插 `xps-a/b/0/1/2/3`、
   tasks.c 里插 `xcs1-4`——逐点收缩挂死位置
3. **寄存器回读**：写不生效 → 读回验证（GICD_IPRIORITYR0 写 0xFFFFFFFF 读回 0）
4. **外部参考**：内核是现成的 GIC 配置范本（/proc/interrupts、dmesg、设备树）
5. **串口交织**：core1 与 u-boot 共用 UART2，输出互相穿插——用 `tr -d '\0'` 清洗 + 特征串 grep

## 4. 方法论总结（三段式）

```
① 先复现 + 完整观测：每次改动的基线日志、串口全程记录、失败留打印
② 先信官方约定，再对照差异：parameter 的 uuid 行、-E 外置 FIT、dts 绑定顺序
   ——"SDK 里现成的写法"就是第一嫌疑参照
③ 源码级修复 → 重建 → 重烧 → 用证据验收（不是"看起来好了"）
```

**三条铁律**：a) 失败路径必须留错误打印（静默失败最坑）；b) 用最小判别实验验证假设
（本地 GPT 生成、dtc 反编译、python 解析 FDT 头、寄存器回读）；c) 三处地址必须手工
同步（link.ld / amp.its load / dts 保留区）——VMA=LMA=加载地址，缺一必崩。
