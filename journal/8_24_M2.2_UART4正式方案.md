## 三、UART4 初始化代码（uart.c，三件套）

```c
#define CRU_BASE        0xFDD20000UL
#define CLKSEL_CON58    0x1E8UL     /* sclk_uart4_mux 位[13:12] */
#define CLKGATE_CON28   0x370UL     /* ★ = 28*4+0x300（不是 0x3B0！）位8=PCLK 位11=SCLK */
#define IOC_BASE        0xFDC60000UL
#define GPIO3B_IOMUX    0x48UL      /* grf_mux_offset 0 + GPIO3 组 0x40 + B 组 8 */

void uart_init(void)
{
    /* ① CRU：mux 选 xin24m（24MHz）+ 去 gate */
    cru_write32(CLKSEL_CON58, 0x3, 2u << 12);
    cru_write32(CLKGATE_CON28, 0x1, 0u << 8);   /* PCLK_UART4 开 */
    cru_write32(CLKGATE_CON28, 0x1, 0u << 11);  /* SCLK_UART4 开 */
    /* ② IOC：GPIO3_B1/B2 → UART4（mux 4）
     *    HIWORD_MASK：B1 位[7:4]→屏蔽[23:20]；B2 位[11:8]→屏蔽[27:24] ★ */
    *(volatile uint32_t *)(IOC_BASE + GPIO3B_IOMUX) =
        (0xFu << 20) | (0xFu << 24) | (4u << 4) | (4u << 8);
    /* ③ UART4 寄存器：波特率 1500000（div=24M/(16*1.5M)=1）8N1 FIFO */
    REG(UART_LCR) = 0x83; REG(UART_DLL) = 1; REG(UART_DLH) = 0;
    REG(UART_LCR) = 0x03; REG(UART_FCR) = 0x01;
}
```

## 四、四个坑（按发现顺序）

### 坑 1：CLKGATE_CON(28) 偏移算错 → UART4 无时钟
`RK3568_CLKGATE_CON(x) = x*4 + 0x300` → CON(28) = 0x370。
我写成 0x3B0（差 0x40）→ 门控写错寄存器 → 时钟没开 → 完全无输出。
**诊断方法**：DIAG 打印 gate28 读回值 + Linux 侧 `cat /sys/kernel/debug/clk/sclk_uart4/clk_rate`。

### 坑 2：IOMUX 写屏蔽错 → TX 引脚没配成 UART4
HIWORD_MASK 语义：高 16 位每位对应低 16 位同一位，写 1 才允许写。
- B1 位[7:4] → 屏蔽 [23:20]
- B2 位[11:8] → 屏蔽 [27:24]
我写成 `(0xF<<16)|(0xF<<20)`（屏蔽 B0+B1）→ **B2(TX) 屏蔽没置 → 写入被忽略 → TX 引脚还是 GPIO → 信号出不去**。
**诊断方法**：DIAG 打印 gpio3b_iomux 读回值（应为 0x440：B1=4 + B2=4；错误时 0x40 只有 B1）。

### 坑 3（最隐蔽）：data-size 保留区不足 → u-boot 踩 BSS/任务栈
固件实际占用到 `_stack_top = 0x7016760`（92KB），但 amp.its 的 data-size=0x10000（64KB）
→ u-boot 的 sysmem 只保留 0x7000000-0x7010000 → **0x7010000+ 的 BSS/任务栈/链表被 u-boot
后续分配踩掉** → `xTaskCreateStatic` 的链表操作死循环（无 [EXC] 无 [FATAL]）。
**修复**：data-size → 0x20000（128KB）。
**诊断方法**：进度标记定位到 xTaskCreateStatic 卡死 → readelf 查 _stack_top → 对比保留区。

### 坑 4：Makefile 无头文件依赖
改 FreeRTOSConfig.h（configASSERT 打 UART2）不触发重编 → 调试信息还在打旧口。
**教训**：改头文件必须 `make clean && make`。

## 七、追加：UART4 无输出事故复盘（16:30-17:20）

### 现象
烧新固件后 UART4 完全无输出，UART2 也看不到 [DIAG]/[core1] —— **core1 压根没被启动**。

### 根因（三个，按发现顺序）
1. **mkimage 版本坑（核心）**：u-boot 的 `fit_get_totalsize` 只认 FIT 根节点
   的 `totalsize` 属性（`u-boot/include/image.h:925`）。Ubuntu 系统 mkimage(2022.01)
   生成 FIT **不写** totalsize；SDK u-boot mkimage(2017.09) **会写**。
   → 用错 mkimage 打包 → u-boot 报 `AMP Error: No totalsize` → core3 不启动。
   **修复**：Makefile 固定 SDK mkimage（已加注释）。
2. **CRU 写使能位修正**（顺带发现）：cru_write32(mask<<16) 的使能位只落在
   数据位 0-1；修正为逐位使能（字段位+16）。读回验证 clksel58=0x2000 生效，
   与芯片默认一致，行为不变（更健壮）。
3. **干净版静默（待查时序）**：5804e925（无标记）UART4 只出 banner+EL1；
   加标记版（98f6b4fd）全部正常（tick 1kHz、t1/t2 输出、U4LSR=0x60）。
   标记是纯打印，疑似时序竞争 → 待做"移除标记"对照实验。

### 排查手段
- 启动日志抓 `AMP Error` → 反查 p1 u-boot 二进制字符串确认修复在不在
- python 解析 FIT 字符串表，对比两套 mkimage 输出
- M1-M6/T1A-D/IRQ 标记定位卡点（这次定位到"一切正常"，干净版问题待查）
- 无网络时串口 base64 分块传文件烧录（wget 不可用时救急通道）

## 八、最终收尾：时序竞争根因定位与正式修复（19:00-20:00）

### 现象复盘
干净版（无任何调试打印）稳定卡在 `banner + el = EL1` 之后，UART4 无 [t1]/[t2]，
UART2 无 [FATAL]/[EXC]，tick 从未触发（实验A1 的 "IRQ fired" 计数 = 0）。

### 定位过程（二分法，全部自诊断）
| 实验 | 内容 | 结果 |
|---|---|---|
| testA | 主函数 M1-M5 + t1 标记 + IRQ 标记全加 | ✅ 全通（tick 1kHz 刷屏） |
| testB | 干净 + 移除 port.c 的 ICC_RPR 断言 | ❌ 卡（RPR 断言无辜） |
| testA1 | 干净 + 只加 IRQ fired 标记 | ❌ 卡（**0 次标记**= 首个 tick 前就挂） |
| testD | 只加主函数 M1-M5 标记 | ✅ 通（gic/队列/任务全过） |
| testG | 干净 + vTaskStartScheduler 前纯延时 3ms | ✅ 通（**纯时序实锤**） |
| testH | 干净 + gic_init 末尾 settle 延时 3ms | ✅ 通（正式修复） |

### 关键推理
- gic_init/queue/tasks/调度器都是**独立编译单元**，机器码在所有版本中完全相同
  → 它们不可能"有时好有时坏" → 唯一变量是 main()/vTask1/IRQ 处理里的**打印时序**
- M 标记（主函数里 gic_init 之后 ~2.5ms 延迟）就是解药 → 纯时序竞争
- 机理：gic_init 完成后立即启动调度器 arm tick/开 IRQ，GIC 尚未完全就绪，
  首个 tick 竞态导致 core1 静默卡死（确切硬件机理未深挖，实证为 ~ms 级 settle）

### 正式修复（testH = 4316c267，当前 p7）
```c
/* gic.c gic_init() 末尾 */
__asm volatile("isb");
for (volatile uint32_t d = 0; d < 3000000u; d++) ;   /* ~3ms GIC settle */
```
- main.c 零调试痕迹；延时语义上属于 GIC 初始化的一部分
- 验证：UART4 [t1]/[t2] 正常，tick 1kHz，UART2 干净（仅 Linux shell）
